# Languages and direction

*Status: the locale is a preference list the shells report and the app
may pin; the framework's own words speak sixteen languages; a
right-to-left scene is the mirror of its left-to-right twin on the
native engine and on the DOM road. Every shell reads the system's
languages before the first frame — macOS, Windows and Android hear a
change while running — and a web page reports the reader's. The proofs
are the core's tests (`a_right_to_left_scene_is_the_mirror_of_its_left_to_right_twin`
is the structural guard, and the whole suite that stood before is the
proof that a left-to-right scene did not move by a byte), the menu
probe reading the mac's words back, and the landing page rendered with
`LANDING_LOCALE=ar`, which seals `<html lang="ar" dir="rtl">`.*

A person asks their computer for Brazilian Portuguese, then English. A
framework that keeps this as one string — "pt-BR" — leaves the app to
guess that "pt" would do, to work out which way the scene reads, and to
rewrite the words the framework itself puts on screen. bunny_ui splits
the work the way SwiftUI and Foundation split it: the framework owns
what only a shell can know (the system's languages), what only the
layout can do (the direction) and its own words; the app owns its
content — the strings, the language preference, and where it is kept.

## The locale is a list

`Locale` is the languages the reader asked for, best first, as one
normalized BCP-47 list behind a counted string: a clone is a count, an
accessor is a slice, and `Locale::parse` is the one normalizer every
shell and page goes through — a POSIX `pt_BR.UTF-8:en`, an
`Accept-Language` header with its weights, a legacy `iw` all come out
as the same canonical tags.

```rust
let locale = Locale::parse("pt_BR.UTF-8:en");        // "pt-BR,en"
locale.identifier();                                   // "pt-BR"
locale.language();                                     // "pt"
locale.region();                                       // Some("BR")
locale.pick(&["en", "pt", "es"]);                      // Some(1) — "pt" serves "pt-BR"
Locale::new("zh-TW").pick(&["zh-Hans", "zh-Hant"]);    // Some(1) — Taiwan implies Hant
Locale::new("ar").direction();                         // LayoutDirection::RightToLeft
```

`pick` walks the preferences in order and answers the index of the
tag that serves one best — an exact match first, then the tag's own
truncation (`pt-Latn-BR`, `pt-Latn`, `pt`), then any tag of the same
language and script — before it moves to the next preference, so a
reader who asked for Japanese, then English, gets English from a
catalog that has no Japanese. It allocates nothing. `direction` reads
the first tag: the script decides where there is one (`ar-Latn` reads
left to right, `az-Arab` right to left), the language otherwise.

## Three doors, one order

| door | who opens it | what it says |
| -- | -- | -- |
| `Runtime::set_system_locale` | the shell | the system's list, before the first frame and again when it moves |
| `App::set_locale`, `Runtime::set_locale` | the app | `Some` pins a locale over the system's; `None` follows the system again |
| `Runtime::set_layout_direction` | the app, a developer | `Some` pins a direction over the locale's own; `None` lets the locale decide |
| `Runtime::with_environment` | a headless seed | what stands until a shell speaks — pin it to keep it |

The locale in effect is the app's pin, else the system's report, else
the seed; the direction in effect is its pin, else the locale's own.
Every door compares before it writes: a shell that reports the same
list twice, a rotation that keeps the size class, a pin that changes
nothing — none of them moves the environment, and the retention is
never rebuilt for a value that stood still. When one does move, the
answer says so, and the shell presents a frame.

The `App` of every shell has the same two doors — `set_locale` and
`locale` — because the pin reaches more than the scene: every open
window, every window still to open, and the words the shell owns (the
mac's menu bar is worded again, the iPad's filed menus, Android's
shortcut groups and its notification channel, a Linux notification's
button). On the web the runtime is the app's, and `Runtime::set_locale`
is the door.

A body reads both from the environment, like a font:

```rust
let locale = environment::<Locale>();              // a count, not a copy
let rtl = environment::<LayoutDirection>().is_rtl();
```

## The app's strings

The framework ships no string catalog of the app's — it ships the
mechanism its own words use, `bunny_ui::catalog`, for an app that
wants the same shape. A `Table` is a BCP-47 tag and a fixed array of
entries in the keys' order; the first table is the source language and
the fallback; an empty entry means "not yet" and falls to the source.
The compiler checks every table's length against the keys, so a table
one word short does not build. The decision happens once —
`Catalog::pick` chooses a table by `Locale::pick` — and from then on
`Strings::get` is an index.

```rust
#[derive(Clone, Copy)]
enum Label { Save, Cancel }
impl catalog::Key for Label {
    const COUNT: usize = 2;
    fn index(self) -> usize { self as usize }
}
static LABELS: Catalog<Label, 2> = Catalog::new(&[
    catalog::Table { tag: "en", entries: ["Save", "Cancel"] },
    catalog::Table { tag: "pt", entries: ["Salvar", "Cancelar"] },
]);

// in a body — or once, at the root, injected for every row below
let strings = LABELS.pick(&environment::<Locale>());
button(text(strings.get(Label::Save)), save)
```

`catalog::fill("{app} beenden", &[("app", "Trinity")])` puts a name
where a template says, because the languages disagree on where that
is. Nothing here reads a file: the tables are the app's to embed, in
the shape its tools write them — and the preference itself (a
settings page that offers a language, and where the choice is kept)
is the app's too. It pins the choice with `App::set_locale` and keeps
it wherever it keeps its settings.

## The framework's words

Nineteen words no app can reach, because the shell writes them: the
mac's app menu (About, Settings…, Services, Hide, Hide Others, Show
All, Quit) and Window menu (Minimize, Zoom, Bring All to Front), the
Edit items every platform lists, a notification's default action on a
Linux desktop, the Android channel's name. `bunny_ui::words` holds
them in sixteen languages — English, Brazilian and European
Portuguese, Spanish, French, German, Italian, Japanese, Simplified and
Traditional Chinese, Korean, Dutch, Russian, Turkish, Polish, Swedish
— following each platform's own glossary where it has one. A word
that names the app is a template with `{app}` where the name goes:
"Quit {app}", "{app} beenden", "{app}を終了".

The app has the last word. `words::install` takes a hook asked first
for every word, in the locale in effect; it answers `Some` with its
own wording or `None` to let the table speak:

```rust
bunny_ui::words::install(|word, locale| match (word, locale.language()) {
    (Word::Quit, "pt") => Some("Sair de {app}".into()),
    _ => None,
});
```

Install it before the menu bar is set, or set the bar again after. A
shell resolves the words once where it builds a menu or posts a
notification (`Words::for_locale`), never per row of a body.

## Right to left

A right-to-left locale mirrors the scene, and the direction is a
branch at each placement — never a pass over the display list after
the fact — so a left-to-right scene costs nothing it did not cost
before and comes out byte for byte the same. What mirrors:

- stacks, frames, padding and flows: leading is the right edge, a
  too-wide child spills left, a flow wraps from the right;
- a split puts its first lane on the right and its grip follows the
  hand; a scroll region starts at its trailing edge, its horizontal
  thumb travels from the right, its vertical bar stands on the left —
  and the offsets an app reads and writes stay LOGICAL, a distance
  from the content's leading edge;
- leading text hugs the right, a truncated line too; a field's fitting
  lines honor direction-relative leading/trailing or centered alignment
  (leading by default) and scroll by the line's own
  reading direction once it overflows, and the caret, the selection
  and the IME's marks follow the line they are on;
- popovers, tooltips and menus open on the mirrored side; a context
  menu hangs down and to the left; the drag label sits on the other
  side of the hand;
- gradients, overlays' anchors and glass run the other way; the
  environment's safe area swaps `leading` and `trailing` (what the
  shell reports stays physical: `set_safe_area` speaks in left and
  right, `.padding` in leading and trailing).

A subtree may read the other way — a quotation in Hebrew inside an
English page, a code sample inside an Arabic one — through the
environment, and only that subtree mirrors:

```rust
quote.environment(|values| values.layoutDirection = LayoutDirection::RightToLeft)
```

Pictures never flip on their own: a photograph reads the same in every
language. A chevron that points the way asks to:

```rust
icon(symbol::CHEVRON).flips_for_right_to_left_layout_direction(true)
```

A box the application owns (`docs/…`, [the README's own section](../README.md#a-box-the-application-owns))
hears the direction it paints in: `PaintCtx::rtl()`, and
`PaintCtx::leading_x(along, width)` for an x measured from the leading
edge; an event carries `direction` too, and a drop names its
`leading_fraction`. The box's own coordinates stay left-origin — what
it does with the direction is its own.

## On the web

The page reports the reader's languages before the wasm starts, so
the first frame is already in them: the glue reads
`navigator.languages`, hands the list through `bunny_set_languages`,
and the shell seeds the runtime with it before adopting a served page
or laying out the first frame. A hydrated page reports the mount's
own `lang` first — the page was built in it, and the adoption must
match it — then the reader's list, and listens for `languagechange`.
The mount (`#app`) carries `lang` and `dir` from the engine, by one
patch when they move, and an island that reads the other way carries
`direction` and `unicode-bidi: isolate` in its own look. Padding is
written logical (`padding-inline`), a trailing alignment is
`text-align: end`, and a horizontal scroll position crosses the border
as the logical offset — the glue negates `scrollLeft` under RTL.

A page rendered ahead of time is sealed in a locale:
`ssr::render_in(root, size, &locale)` lays the scene out in its
direction and answers `lang` and `dir` beside the HTML and CSS;
`render_document_in` writes them on `<html>`. The landing page's
`render` example takes `LANDING_LOCALE`.

## What each platform reads

| | macOS | Windows | Linux | iOS | Android | web |
| -- | -- | -- | -- | -- | -- | -- |
| the list | `NSLocale.preferredLanguages` | `GetUserPreferredUILanguages` | `LANGUAGE`, else `LC_ALL`, `LC_MESSAGES`, `LANG` | `NSLocale.preferredLanguages` | the configuration's `LocaleList` | `navigator.languages` |
| hears a change | `NSCurrentLocaleDidChangeNotification` | `WM_SETTINGCHANGE` | no — the environment does not move while the process runs | no — a change of language relaunches the app | the configuration change; the sample manifest keeps the activity through `locale` and `layoutDirection` | `languagechange` |
| the words it owns | the app and Window menus, the edits | — | a notification's button | the Settings row, the edits | the shortcuts helper's rows, the channel's name | — |

No shell reports a direction: it follows the locale in effect, and a
developer who wants to see a scene mirrored without changing its
language pins one with `Runtime::set_layout_direction`.

## Honest edges

A line that mixes directions — Arabic with a Latin name in it — is
placed by its first letter; the caret and the highlights inside it are
approximate until a bidi pass joins. The Linux text engine has no such
pass at all. UIKit's standard menu rows are matched by their English
title. A served page read in another language than it was built in
adopts in the served one, then re-runs once and diffs — a visible
flip; serve per `Accept-Language` to avoid it. On Android,
`LocaleList.toLanguageTags` needs API 24; the sample's minimum is 30.
